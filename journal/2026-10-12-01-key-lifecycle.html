삭제 승인이 있어도 키를 바로 삭제할 수 없는 이유

기록일 2026-10-12

사용 중인 키의 삭제 충돌에서 출발해, 독점 핸들·기존 서명의 유효성·유출 키의 신뢰 철회를 구분했다.

키 삭제 · 동시성 · 키 폐기

공부를 시작한 질문질의응답에서 수정한 이해사용 중인 객체: 별도 조회보다 독점 열기의 결과가 중요하다대기 삭제를 도입한다면 정해야 하는 것삭제된 키의 공개키는 어디에서 얻는가내 구현과 연결한 부분다음에 확인할 것

공부를 시작한 질문

같은 키를 다른 세션이 사용 중인데 정상적인 삭제 승인을 받았다면, 즉시 삭제해도 될까?

처음 이해했던 내용

기존 사용이 끝날 때까지 기다리고 새 요청을 막기 위해 세마포어가 필요하다고 생각했다. 또 개인키를 삭제하면 공개키를 다시 얻을 수 없으므로 기존 서명 검증도 실패한다고 답했다.

↑ 목차로

질의응답에서 수정한 이해

  • 사용 중이면 실패시키는 정책과 사용 종료를 기다리는 정책은 서로 다른 설계다. 현재 코드는 독점 열기에 실패하면 오류를 반환하며 자동으로 기다리지 않는다.
  • ACCESS_WRITE_META는 같은 객체의 다른 열린 핸들과 충돌한다. 정확한 오류는 ACCESS_CONFLICT이며, 대상 키 지문 불일치의 ACCESS_DENIED와 구분한다.
  • 승인 검증에 성공해도 실제 삭제 대상이 바뀌지 않았는지 확인해야 한다. 독점적으로 연 같은 핸들을 지문 검사부터 삭제까지 유지한다.
  • 개인키 삭제는 이미 만들어진 서명을 무효로 바꾸지 않는다. 공개키와 메시지·서명을 확보했다면 개인키 없이 검증할 수 있다.
  • 유출된 개인키 복사본은 보드에서 삭제해도 없어지지 않는다. 검증자의 기존 키 신뢰 철회와 새 키로의 교체가 별도로 필요하다.
↑ 목차로

사용 중인 객체: 별도 조회보다 독점 열기의 결과가 중요하다

같은 객체를 세션 A가 먼저 열고 있으면, 세션 B의 ACCESS_WRITE_META 열기는 충돌한다. 반대로 B가 독점 열기에 먼저 성공하면 그 핸들을 유지하는 동안 A의 새 열기가 충돌한다. 별도의 “사용 중인가?” 조회 결과와 실제 삭제 사이에 생기는 경쟁을 피할 수 있다.

지문 확인 후 핸들을 닫고 Object ID로 다시 열면 그 사이 다른 실행 흐름이 키 A를 같은 이름의 키 B로 바꿀 수 있다. 같은 핸들로 삭제하는 이유는 챌린지가 바뀌어서가 아니라, 검사한 바로 그 객체를 삭제하기 위해서다.

운영 서명 키와 삭제용 테스트 키는 현재 서로 다른 객체다. “서명에 사용 중인 바로 그 키를 삭제한다”는 질문은 동일 객체에 대한 설계 시나리오이며 현재 보드에서 실행한 시험으로 보지 않는다.

↑ 목차로

대기 삭제를 도입한다면 정해야 하는 것

기존 사용을 마친 뒤 삭제하려면 키별 삭제 대기 상태를 공유하고 해당 키의 신규 사용을 차단해야 한다. 타임아웃, 사용자가 핸들을 계속 잡는 경우, 실패·취소 처리까지 정해야 하므로 세마포어 하나만 추가한다고 정책이 완성되지는 않는다.

첫 구현에서는 충돌을 반환하고 새 요청으로 재시도하는 정책도 타당하다. 승인 여부는 실행 권한을 판단하고, 객체 열기는 현재 자원 상태를 판단한다.

↑ 목차로

삭제된 키의 공개키는 어디에서 얻는가

현재 CA의 fetch_signing_public_key는 TA에서 n·e를 받아 메모리의 EVP_PKEY 객체로 구성한다. run_authorized_signing은 이를 사용한 뒤 해제한다. 데이터 서명 공개키를 자동으로 파일에 보관하는 흐름은 아니다.

--sign-public-key는 공개 성분을 출력하며, 재부팅 시험의 파일 저장은 셸 리다이렉션으로 수행했다. 출력은 PEM이 아니고 현재 CA에는 해당 파일을 읽는 독립 검증 기능이 없다. 현재 CA가 삭제된 객체에서 공개키 조회에 실패하는 것과, 별도로 보관한 공개키로 기존 서명을 검증할 수 있다는 것은 양립한다.

공격자가 공개키만 갖고 있다면 서명을 새로 만들 수 없다. 유출된 개인키를 보유한 경우 계속 서명할 수 있다. 암호학적으로 유효한 서명이라도 폐기된 키라면 수용하지 않도록 검증 정책을 갱신해야 한다.
