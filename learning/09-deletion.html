질문의 출발점

Object ID로 열었는데 왜 공개키 지문을 다시 비교해야 하는가?

이해가 바뀐 지점

approved_key_fingerprint_sha256를 공개키 자체로 생각한 부분을 정정했다. 같은 Object ID 아래 새 키가 생길 수 있으므로, 요청 시점의 키 내용까지 다시 확인한다는 의미를 정리했다.

왜 테스트 키 생성과 삭제를 분리했는가?

삭제 명령이 없는 키를 자동 생성해서 지우면 무엇을 삭제했는지 모호해진다. 테스트 키 생성은 명시적으로 수행하고, CA의 삭제 명령 하나가 준비·대기·제출을 같은 세션에서 이어간다. 운영 서명 키와 테스트 키도 구분한다.

키 A가 키 B로 바뀌면?

승인 대기 중 같은 이름의 객체가 새 키로 대체될 수 있다. 승인 서명이 올바르더라도 현재 키의 공개키 지문이 승인 대상과 다르면 삭제를 거부한다. 승인 확인과 대상 확인은 다른 검사다.

왜 검사한 핸들로 바로 삭제하는가?

검사 후 핸들을 닫고 이름으로 다시 열면 검사한 객체와 삭제할 객체 사이에 틈이 생긴다. 현재 helper는 ACCESS_WRITE_META로 열고 지문을 비교한 바로 그 핸들로 삭제한다. 사용 중 충돌은 오류로 처리하며 모든 세션의 자동 종료·대기는 구현하지 않았다.

실패하면 무엇을 정리하는가?

지문 조회나 비교 실패 시 열린 핸들만 닫고 객체는 남긴다. 삭제 API가 핸들을 소비한 뒤 중복으로 닫지 않는다. 오류 코드를 무조건 bool로 축소하기보다 원인을 유지한다.

보드 로그는 무엇을 보여줬는가?

사용자가 제공한 1.0-r0.11 로그에는 테스트 키 생성, 승인된 삭제 성공과 종료 0, 이후 지문 조회의 ITEM_NOT_FOUND가 있다. 이것은 정상 삭제 경로의 증거이며 잘못된 승인·동시 사용·대상 교체 시험 성공을 대신하지 않는다.
