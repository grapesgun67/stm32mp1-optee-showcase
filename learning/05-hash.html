여러 번 UPDATE해도 하나의 SHA-256인 이유

정리일 2026-10-11 · 소스 대조 bdb8bd8

질문의 출발점정리한 이해코드와 연결

질문의 출발점

DigestUpdate가 입력 버퍼에 해시를 갱신하는가? Final은 무엇을 끝내는가?

이해가 바뀐 지점

입력 버퍼와 해시 연산 내부 상태를 구분했다. 여러 조각을 순서대로 공급하는 것과 조각별 해시를 다시 조합하는 것은 다른 연산임을 정리했다.

↑ 목차로

정리한 이해

  1. 01BEGIN: 연산 준비
  2. 02UPDATE: 입력 조각 누적
  3. 03FINAL: 최종 다이제스트 출력
  4. 04연산 자원 정리

UPDATE를 여러 번 호출하는 이유는?

전체 파일을 메모리에 올리지 않고 조각으로 처리할 수 있다. 같은 바이트열을 같은 순서로 공급하면 나누는 크기가 달라도 최종 SHA-256은 같다. 조각마다 별도 해시를 계산해서 이어 붙이는 방식이 아니다.

입력 버퍼가 해시값으로 바뀌는가?

Update는 연산 핸들이 관리하는 내부 상태를 갱신한다. Final은 마지막 입력을 처리하고 최종 다이제스트를 출력 버퍼에 쓴다. 현재 서비스는 앞선 Update로 데이터를 공급하고 Final에서 결과를 받는다.

API 호출 순서도 검사해야 하는가?

BEGIN 없이 UPDATE하거나 종료 후 FINAL을 반복하는 것을 상태로 거부한다. 재BEGIN 정책과 실패·세션 종료 시 연산 해제를 함께 정의해야 한다.

왜 %02x와 putchar를 사용했는가?

32바이트 결과를 바이트마다 두 자리 16진수로 표시한다. 마지막 putchar는 줄바꿈 한 문자를 출력할 뿐이며 printf로 바꿀 수도 있다. 출력 형식과 해시 알고리즘은 별개다.

서명 전에 CA에서도 SHA-256을 계산하는 이유는?

현재 서명 명령은 원문 대신 SHA-256 다이제스트를 계약으로 사용한다. 원문과 다이제스트를 어느 계층에서 계산·검증하는지 명확해야 하며 이중 해싱을 혼동하지 않아야 한다.
