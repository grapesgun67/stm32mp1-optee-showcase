Secure Boot와 롤백 방지는 어디서 시작되는가

정리일 2026-10-11 · 소스 대조 bdb8bd8

질문의 출발점정리한 이해코드와 연결

질문의 출발점

검사 코드와 기준도 되돌릴 수 있다면 롤백 방지는 불가능한가?

이해가 바뀐 지점

버전 숫자만 추가하는 방안에서, 되돌릴 수 없는 기준과 검사 코드의 보호가 함께 필요하다는 점으로 확장했다. Boot ROM 작성과 제품 Secure Boot 통합 업무도 구분했다.

Secure Boot는 무엇을 보장하는가?

허가된 부팅 코드를 검증하고 실패 시 실행을 차단하도록 구성한다. 정상 서명된 코드의 취약점이나 실행 중 Linux 침해까지 자동으로 막지 않는다. 복구 경로도 검증 정책에 포함해야 한다.

최초 부트로더는 누가 검증하는가?

칩의 Boot ROM과 보호된 신뢰 기준에서 시작한다. 제품 개발은 보통 제조사 ROM 위에 TF-A·U-Boot·보안 펌웨어의 검증, 키 관리, 제조 설정과 실패 정책을 연결한다. ROM 자체 개발은 칩 설계·검증과 맞물리는 별도 영역이다.

RPMB는 빌드하면 생기는가?

지원 저장장치에 있는 하드웨어 영역을 소프트웨어가 사용하도록 구성한다. 인증과 쓰기 카운터로 재전송을 방어한다. RPMB 인증키는 TA의 RSA 서명키와 다르며 최초 키 등록은 되돌릴 수 없는 절차이므로 제품 제조 정책이 필요하다.

버전 검사는 어떻게 연결하는가?

서명으로 보호한 이미지 버전과 보호된 최소 허용 버전을 비교한다. RPMB의 쓰기 카운터를 펌웨어 버전과 동일시하지 않는다. RPMB는 기준 저장의 기반이고 실제 허용·갱신 정책은 서비스나 로더가 구현해야 한다.

제품 적용에서 무엇이 더 필요한가?

하드웨어 지원, OP-TEE 설정, 비밀키 공급, 부팅 코드 보호와 버전 정책, 업데이트 실패·복구 시험이 함께 필요하다. CFG_RPMB_FS=y 한 줄이나 재부팅 후 키 유지 결과만으로 전체 롤백 방지를 선언할 수 없다.
