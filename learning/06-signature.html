서명 검증은 데이터가 참이라는 증명이 아니다

정리일 2026-10-11 · 소스 대조 bdb8bd8

질문의 출발점정리한 이해코드와 연결

질문의 출발점

n과 e로 무엇을 만들며, 공개키 검사와 서명 검증은 어떻게 다른가?

이해가 바뀐 지점

공개키의 유효성 검사, 원문에 대한 서명 검증, 원문 내용의 사실 여부를 구분했다. 승인용 서명과 TA가 만드는 데이터 서명도 서로 다른 키와 목적을 가진다는 점을 정리했다.

↑ 목차로

정리한 이해

  1. 01TA 공개키 n·e 내보내기
  2. 02CA 공개키 객체 구성
  3. 03TA가 다이제스트 서명
  4. 04CA가 정상·변조 데이터 검증

바이트열에서 EVP_PKEY까지 왜 단계가 많은가?

BN_bin2bn으로 RSA 정수를 만들고, OSSL_PARAM_BLD에 이름 있는 n·e 파라미터를 넣어 전달 목록을 만든다. EVP_PKEY_fromdata는 이 정보로 공개키 객체를 구성한다. PUBLIC_KEY 선택은 개인키까지 가져오는 요청이 아니다.

public_check는 무엇을 검사하는가?

구성한 공개키의 알고리즘별 유효성을 검사한다. 그 키가 신뢰하는 장치의 키라는 신원 확인이나 특정 메시지 서명 검증은 아니다. 후자는 EVP_PKEY_verify와 지정한 알고리즘·다이제스트·서명으로 수행한다.

2048과 256과 32는 무엇이 다른가?

현재 RSA 키 크기는 2048비트, RSA 서명 길이는 256바이트, SHA-256 결과는 32바이트다. 개발자가 알고리즘과 지원 범위에 맞춰 키 크기·패딩·해시 계약을 정하며 값들이 같은 뜻은 아니다.

서명은 개인키 암호화인가?

이 문서에서 서명은 암호학적 디지털 서명을 뜻한다. RSA 서명은 정해진 인코딩·패딩·해시 규칙을 따르므로 일반적인 파일 암호화·복호화처럼 설명하지 않는다. 서명된 데이터가 온도 범위에 맞는지, 실제 센서 값인지는 별도 검증 문제다.

개인키를 내보내지 않으면 충분한가?

키 추출과 키 기능 악용은 별개다. 임의 요청에 서명해 주면 공격자는 키를 읽지 않고도 원하는 서명을 받을 수 있다. 그래서 외부 승인 정책을 추가했다.

개발 저장소의 portfolio-hello 기준 함수·파일입니다. 공개된 기존 발췌는 별도의 과거 스냅샷이며 함수명이 다를 수 있습니다.

  • ta/entry.c: sign_message_digest_with_stored_key
  • RSA 구현 설명
근거와 확인 범위

정상 데이터 검증 성공과 변경 데이터 거부는 해당 서명 시험의 결과다. 외부 제품이 이 서명을 소비하는 기능까지 구현했다는 의미는 아니다.

  • OpenSSL EVP_PKEY_fromdata
  • NIST digital signature
