clone한 코드가 보드에서 실행되기까지

정리일 2026-10-11 · 소스 대조 bdb8bd8

질문의 출발점정리한 이해코드와 연결

질문의 출발점

소스와 커밋 저장소는 왜 분리했으며, CA/TA를 바꿀 때마다 전체 이미지를 만들어야 할까?

이해가 바뀐 지점

portfolio-hello를 레이어로 생각했던 질문에서 출발해, 자체 레이어·레시피·패키지·전체 이미지를 구분했다. 새 터미널의 환경 초기화와 같은 터미널의 반복 빌드도 분리했다.

clone만 하면 바로 빌드할 수 있는가?

개발 저장소는 고정 manifest와 설정·자체 레이어를 보관한다. 처음에는 외부 원본 소스 복원, 호스트 의존성 준비, 사용자 EULA 수락과 환경 초기화가 필요하다. 이 공개 전시 저장소는 Yocto 빌드 저장소가 아니다.

portfolio-hello는 레이어인가?

meta-portfolio가 레이어이고 portfolio-hello_1.0.bb는 레시피다. 레시피 작성은 개발자의 작업이다. 패키지를 만드는 것과 st-image-weston 이미지에 설치 대상으로 포함하는 것은 별도 단계다.

언제 전체 이미지를 만드는가?

CA/TA 반복 개발은 해당 레시피의 패키지를 빌드해 보드에 갱신할 수 있다. 새 SD 배포 이미지가 필요하면 전체 이미지 타깃을 빌드한다. BitBake는 재사용 가능한 작업까지 무조건 처음부터 다시 수행하지 않는다.

무엇을 확인해야 실제 포함을 말할 수 있는가?

활성 BUILDDIR, 이미지 manifest의 패키지 항목, oe-pkgdata-util의 설치 파일 목록, 보드의 설치 버전과 실행 결과를 차례로 확인한다. 다른 빌드 디렉터리의 local.conf를 고치면 원하는 빌드에 반영되지 않을 수 있다.

링크와 실행 파일은 어떻게 조사했는가?

DEPENDS와 링크 옵션을 확인하고, deb를 임시 위치에 풀어 내부 ELF에 readelf -d를 사용하면 NEEDED 항목을 확인할 수 있다. deb 자체는 ELF가 아니므로 readelf로 직접 분석하지 않는다.

코드와 연결

개발 저장소의 portfolio-hello 기준 함수·파일입니다. 공개된 기존 발췌는 별도의 과거 스냅샷이며 함수명이 다를 수 있습니다.

  • portfolio-hello_1.0.bb: 의존성, 컴파일, 설치
  • env.sh / scripts/setup.py: 개발 저장소의 환경 준비
  • 기존 배포·시험 절차
  • 보드 실증
근거와 확인 범위

기존 공개 환경 로그는 패키지 1.0-r0.10과 설치 파일을 기록한다. 새로운 빌드 재현 시험을 이번 문서 작성 중 수행한 것은 아니다.
