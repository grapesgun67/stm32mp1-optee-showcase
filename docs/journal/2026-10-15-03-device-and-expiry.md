# 챌린지가 있어도 장치 출처와 승인 만료는 별도 문제다

기록일: 2026-10-15

보드 간 승인 재사용, 장치 식별값의 신뢰, 시간 응답의 최신성을 확장 설계로 검토했다.

## 공부를 시작한 질문

서명과 챌린지가 유효하면 어느 보드의 요청인지, 얼마나 오래된 승인인지까지 알 수 있는가?

### 처음 이해했던 내용

보드 간 재사용은 챌린지로 막을 수 있다고 답했다. 이후 승인자가 요청 출처를 잘못 판단하는 경우와 장시간 열린 세션의 미사용 승인은 별도 문제임을 구분했다.

## 질의응답에서 수정한 이해

- 서로 다른 난수 챌린지를 사용하는 세션 사이에서 옛 승인은 검증되지 않는다. 장치 식별값이 없으면 무조건 재사용된다는 설명은 부정확하다.
- 챌린지는 요청을 연결하지만 승인자에게 실제 장치 출처를 증명하지는 않는다.
- 아직 소비되지 않은 요청에는 시간 제한이 없으면 오래된 승인이 유효할 수 있다.
- 서명된 시간 응답이라는 예시는 별도 설계 가정이며, 모든 시간 서버나 현재 TA가 그런 기능을 제공하는 것은 아니다.

## 보드 A의 승인이 B에서 통과하지 않는 조건

TA UUID와 승인 공개키가 같아도 각 TA가 독립적인 챌린지를 세션에 저장하고 재구성한다면 A에 대한 서명은 B의 대기 요청과 일치하지 않는다. 이 점을 먼저 확인했다.

하지만 공격자가 B에서 받은 요청을 노트북에 A의 요청이라고 소개하고 승인을 얻으면, B는 자신의 요청에 대한 유효한 승인을 받은 것이다. 재사용 방지와 승인자의 장치 식별은 다른 문제다.

## 장치 식별값을 넣는 것과 출처 증명

확장 설계에서는 TA가 신뢰할 수 있게 확보한 자기 장치 식별값을 요청에 포함하고 검증 시에도 자기 값을 사용한다. 공격자가 B를 A로 고쳐 승인받으면 B의 재구성과 달라 검증에 실패한다.

노트북에서도 표시된 식별값이 실제 장치의 것인지 확인할 신뢰 경로가 필요하다. 등록된 장치별 키로 요청 서명을 확인하거나 인증된 연결을 사용하는 방식 등을 검토할 수 있다. CA가 보낸 이름을 그대로 표시하는 것만으로는 출처 인증이 아니다.

현재 132바이트 요청에는 장치 식별 필드가 없다. 이 내용을 적용하려면 프로토콜 버전과 직렬화·검증 코드를 함께 변경해야 한다. 이번 학습에서 구현한 기능으로 표시하지 않는다.

## 챌린지는 시계가 아니다

세션이 계속 열려 있고 대기 요청이 소비되지 않았다면 하루 뒤 받은 승인도 현재 검사만으로 만료되었다고 판단할 수 없다. 요청 생성 시점과 실행 시점 사이의 시간을 제한하는 정책이 별도로 필요하다.

같은 세션에서의 경과 시간은 플랫폼이 제공하는 신뢰할 수 있는 단조 시간 기준을 검토할 수 있다. 재부팅을 넘겨 유지할지는 별도 요구사항이다. CA가 임의로 제공한 시각은 탈취된 CA가 바꿀 수 있으므로 기준으로 그대로 신뢰할 수 없다.

## 시간 서버 응답에도 인증과 최신성이 필요하다

TA는 이 프로젝트에서 보드의 Secure World에서 실행된다. 외부 시간 서버를 쓴다는 것은 별도의 설계 선택이다. 예시로 서버가 시간값에 전자서명을 붙이고 TA가 신뢰한 서버 공개키로 확인할 수 있다.

서명이 정상이어도 어제의 응답을 재전송한 것일 수 있다. 요청 챌린지와 시간값을 함께 서명하면 이번 요청과 연결할 수 있지만, 응답을 오래 지연하는 문제와 허용 오차·시간 경과 측정도 별도로 고려해야 한다.

시간값을 TA 메모리에 저장하는 것만으로 시간이 흐르거나 최신성이 보장되지는 않는다. 현재 보드의 시간 보장과 서버 연동은 확인·구현하지 않았다.
