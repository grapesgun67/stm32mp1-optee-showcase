# 키 삭제·신뢰 철회·롤백 방지는 서로 다른 작업이다

기록일: 2026-10-14

두 서명키의 역할과 유출 피해를 구분하고, 공개키 신뢰 기준에서 TA 롤백 방지까지 연결했다.

## 공부를 시작한 질문

데이터가 참인지 보장하지 못한다면 왜 서명하는가? 유출된 개인키를 TA에서 삭제하면 공격자의 서명도 막을 수 있는가?

### 처음 이해했던 내용

두 개인키가 서로 다른 대상을 서명한다는 점은 구분했다. 하지만 데이터 서명키가 유출되어도 승인 절차를 거쳐야 한다고 생각했고, TA에서 키를 삭제하면 외부 검증도 막힌다고 답했다.

## 질의응답에서 수정한 이해

- 서명은 데이터 내용의 진실성이나 안전성을 자동으로 보장하지 않는다. 신뢰하는 키의 서명인지와 서명 대상의 무결성을 확인한다.
- TA 데이터 서명키가 유출되면 공격자는 TA와 승인 절차를 거치지 않고 외부에서 서명할 수 있다.
- TA의 키 삭제는 공격자가 복사한 개인키와 검증 서버의 공개키를 삭제하지 않는다. 검증 측의 신뢰 철회가 별도로 필요하다.
- 신뢰 철회는 옛 키의 사용을 거부하는 정책이다. 롤백 방지는 옛 키를 허용하던 코드·상태로 되돌아가지 못하게 하는 보호다.
- 공개키의 형식이 정상인 것과 그 키의 소유자에게 승인 권한이 있는 것은 다르다.

## 두 개인키는 무엇에 서명하는가

TA 데이터 서명용 개인키는 승인된 원문의 SHA-256 다이제스트에 RSA PKCS#1 v1.5 + SHA-256 방식으로 서명한다. 노트북 승인용 개인키는 챌린지·동작·대상 키 지문·원문 다이제스트 등을 담은 승인 요청 전체를 해싱해 서명한다.

승인용 공개키는 TA가 노트북 승인을 검증하는 데 쓰고, 데이터 서명용 공개키는 CA나 외부 검증자가 결과 서명을 검증하는 데 쓴다. 노트북 승인 도구와 외부 결과 검증 서버는 다른 역할이다.

## 실무에서 서명을 사용하는 두 사례

Uptane의 ECU 버전 보고는 ECU 키로 서명하고 검증 측에서 확인하는 사례다. 이 프로젝트를 확장한다면 ECU 키를 TA에 보관하는 설계를 생각할 수 있다. 다만 실제 Uptane 구현이나 업체의 OP-TEE 사용을 이 프로젝트의 성과로 주장하는 것은 아니다.

Android Key Attestation은 키의 보호 속성 등에 관한 서명된 인증서 체인을 외부에서 검증하는 사례다. 챌린지·체인·보호 속성을 확인한다. 임의 데이터 서명만 구현했다고 하드웨어 증명 기능이 완성되는 것은 아니다.

공통점은 보호된 키의 서명을 외부에서 검증한다는 것이다. 무엇을 서명할지 결정하는 정책과, 보고 내용의 신뢰할 수 있는 출처도 함께 설계해야 한다. 정상 서명된 펌웨어에도 버그가 있을 수 있다.

## 유출된 키의 복사본은 TA의 삭제 명령으로 사라지지 않는다

승인 개인키만 유출되면 공격자는 새 요청을 얻어 유효한 승인을 만들 수 있다. 챌린지는 과거 서명의 재사용을 제한하지만 유출 키로 만드는 새 서명까지 막지 않는다. 정상적인 격리와 구현을 전제로, 이것이 곧 TA 데이터 개인키의 직접 추출을 뜻하지는 않는다.

데이터 서명용 개인키가 유출되면 공격자는 자기 컴퓨터에서 데이터를 서명할 수 있다. 검증 서버가 옛 공개키를 계속 신뢰하면 그 서명도 받아들일 수 있다. 새 공개키를 추가해도 옛 공개키를 계속 허용하면 해결되지 않는다.

키 삭제는 관리 중인 저장소의 키를 없애는 것, 키 교체는 새 키를 사용하는 것, 신뢰 철회는 검증 측이 옛 키로 만든 서명을 허용하지 않는 것이다. 공개키를 과거 기록용으로 보관하면서 새 요청에는 사용하지 않을 수도 있다.

## 승인키 교체와 TA 롤백 방지의 구체적인 차이

현재 하드코딩 방식의 승인키 교체는 노트북이 새 개인키를 사용하고 TA가 새 공개키만 검증에 사용하도록 수정·배포하는 것이다. 노트북만 바꾸면 새 승인은 실패하고 옛 개인키의 새 승인은 통과할 수 있다.

TA 파일 검증용 공개키는 승인용 공개키와 별개다. 구버전 TA도 정상 서명되어 있다면 파일 서명 검사만으로는 거부할 수 없다. 구버전 안의 옛 승인 공개키가 다시 신뢰 기준이 될 수 있다.

OP-TEE 4.0 공식 문서에는 REE-FS TA 버전을 ta_ver.db로 관리하며 CFG_TA_VERSION으로 TA 버전을 설정하고, 유효한 롤백 방지에 CFG_RPMB_FS=y가 필요하다고 설명되어 있다. 먼저 기존 지원을 확인해야 하며 반드시 새 검증 코드를 개발해야 한다는 뜻은 아니다.

Yocto는 코드·설정을 빌드하는 단계다. 실제 적용에는 대상 OP-TEE 구성, 지원 저장장치, RPMB 프로비저닝, 버전 관리와 구버전 거부 시험이 필요하다. OP-TEE 자체를 구버전으로 되돌리는 경로도 별도로 보호해야 한다. 현재 보드의 RPMB 가용성이나 롤백 방지 완료를 확인한 것은 아니다.

## 공개키는 공개되어도 되지만 공격자의 키로 교체되면 안 된다

TEE_PopulateTransientObject는 기존 키 속성을 객체에 채우는 API이고, TEE_GenerateKey는 새 키를 생성한다. RSA 공개키 값은 n과 e다. p는 키 생성에 쓰이는 비밀 소수 중 하나이며 공개키 요소가 아니다.

검증은 신뢰한 공개키, 받은 승인 서명, TA가 재구성한 요청의 다이제스트를 사용한다. CA가 임의 공개키를 보낼 수 있고 TA가 그대로 신뢰한다면 공격자가 자기 키 쌍으로 만든 승인도 검증될 수 있다.

키 등록 파일에 서명을 붙여도 그 등록 서명을 검증하는 키까지 공격자가 교체할 수 있으면 의미가 없다. 결국 공격자가 바꿀 수 없는 신뢰 기준이 필요하다. 현재 승인 서비스에서는 TA에 내장한 승인 공개키가 그 기준이며 TA 자체의 보호는 부팅·로딩 신뢰 체인으로 이어진다.

개인키에는 기밀성 보호가 필요하고 공개키에는 무결성과 신뢰 출처 보호가 필요하다. 공개키 n, e를 안다는 사실만으로 승인 서명을 생성할 수는 없다.

## 내 구현과 연결한 부분

현재 TA의 공개키 import·승인 검증 경로와 데이터 서명 경로를 구분해 읽었다. 롤백 방지는 프로젝트 CA 명령을 추가하는 문제와 OP-TEE 로딩 정책·플랫폼 보호 문제를 구분해 검토해야 한다.

- ta/entry.c: verify_approval_signature — 승인 공개키 객체로 요청 서명 검증
- ta/entry.c: sign_message_digest_with_stored_key — 저장된 데이터 서명키 사용
