# 내부 복사·요청 소비·키 지문은 각각 무엇을 지키는가

기록일: 2026-10-12

삭제 처리 여섯 단계를 다시 설명하며, 입력 고정과 일회 사용과 대상 동일성의 역할을 분리했다.

## 공부를 시작한 질문

서명과 지문을 왜 따로 복사하고, 실패할 수도 있는데 왜 요청을 먼저 소비하는가?

### 처음 이해했던 내용

승인 서명을 복사하는 목적을 재전송 방지라고 답했다. 같은 핸들로 삭제하는 이유도 챌린지가 바뀌기 때문이라고 혼동했다. 256바이트 서명과 32바이트 다이제스트의 명칭도 다시 구분할 필요가 있었다.

## 질의응답에서 수정한 이해

- 공유 메모리의 승인 서명 복사는 이번 호출에서 검증할 입력을 TA 내부에 고정하기 위한 작업이다. 요청 재사용 방지와는 별개다.
- 승인 대상 지문 복사는 세션 상태를 곧 지우더라도, 이번 호출의 마지막 대상 비교에 쓸 기준을 남기기 위한 작업이다.
- 요청 소비는 다음 호출이 같은 대기 상태와 챌린지를 재사용하지 못하게 한다. 로컬 배열에 바이트가 남아 있는지가 재사용을 허용하는 조건은 아니다.
- 독점 핸들 유지는 지문을 확인한 객체와 삭제할 객체가 같도록 하기 위한 작업이다. 챌린지 생성·변경과 관계없다.
- 지문은 식별·대조라는 용도를 강조한 말이고 다이제스트는 해시 출력이라는 형태를 말한다. 현재 공개키 지문도 SHA-256 다이제스트다.

## 첫 번째 복사: 검증할 서명을 내부에 고정한다

공유 버퍼에 서명 A가 있고 TA가 이를 읽는 동안 악성 Linux가 B로 바꿀 수 있다. 입력 길이·타입이 맞는다는 사실만으로 내용의 일관성까지 보장되지 않는다. 현재 코드는 타입·상태·길이·NULL 검사를 거쳐 서명 내용을 내부 배열에 복사하고 그 배열을 검증한다.

복사 완료 뒤 원래 공유 버퍼가 바뀌어도 내부 복사본은 바뀌지 않는다. 다만 복사 중 변경될 가능성을 복사 자체가 제거하지는 않으므로 결과에 대한 서명 검증은 여전히 필요하다. 내부 복사본을 검증하고 다시 공유 버퍼를 사용한다면 검사와 사용 사이의 틈이 남는다.

포인터만 복사하면 같은 공유 메모리를 가리킨다. 보호를 위해 필요한 것은 해당 길이의 내용 복사와, 검증된 복사본을 실제 처리에도 사용하는 것이다. 초반 유효성 검사만 보고 취약점이 있다고 단정하지 않고 이후 사용 경로까지 확인해야 한다.

## 두 번째 복사: 지울 세션 값 중 이번 처리에 필요한 것을 남긴다

삭제 준비에서 키 A의 공개키 지문을 세션에 저장한다. 실제 제출 처리에서는 지문을 로컬 배열로 복사한 뒤 요청을 재구성하고 clear_pending_approval로 세션의 챌린지·지문 등을 지운다.

그 뒤 승인 서명 검증이 성공하면 현재 키를 열어 로컬 배열에 남긴 A 지문과 비교한다. 원본 세션을 지웠어도 별도 내용 복사본은 유지되므로 비교할 수 있다. 단순 포인터 별칭이었다면 원본을 지울 때 비교 기준도 잃는다.

## 왜 삭제 성공 전에 요청을 소비하는가

현재 정책은 승인 하나를 “성공할 때까지 계속 사용할 허가”가 아니라 “사전 검사를 통과한 처리 시도 한 번의 허가”로 사용한다. 실제 검증·삭제 전에 소비하면 이후 어느 실패 분기에서도 같은 대기 요청이 남지 않게 할 수 있다.

예를 들어 서명은 정상인데 객체 열기가 ACCESS_CONFLICT로 실패해도 재시도에는 새 준비와 승인이 필요하다. 준비 없이 재제출하면 상태 검사에서 거부되고, 새 준비 뒤 옛 서명을 제출하면 새 챌린지에 맞지 않아 검증에 실패한다.

이 방식이 유일한 정답은 아니다. 일시적 실패에 재승인이 필요한 비용이 있다. 재시도 허용 정책을 설계하려면 허용 오류·유효기간·대상 동일성·상태 전이를 정해야 한다. 현재 구현은 사전 형식 오류에서는 소비 지점에 도달하지 않는다는 구분도 유지한다.

## 삭제 요청 다이제스트와 공개키 지문 구분

삭제 요청은 도메인·TA UUID·삭제 동작 번호·공개키 지문·챌린지·Object ID 해시로 재구성한다. 이 132바이트를 SHA-256 처리한 결과가 승인 요청 다이제스트다. 삭제 요청의 마지막 필드는 메시지 해시가 아니라 대상 Object ID의 해시다.

공개키 지문은 현재 SHA-256(n의 고정 길이 256바이트 || e의 고정 길이 3바이트)로 계산한다. 긴 공개키를 짧은 값으로 식별·대조하므로 지문이라고 부르며 공개키 자체는 아니다. PEM 텍스트 전체를 해싱하면 다른 값이 될 수 있으므로 계산 형식도 계약이다.

공개키 지문과 승인 요청 다이제스트는 모두 32바이트이지만 입력과 용도가 다르다. 요청 파일은 132바이트, 받은 RSA-2048 승인 서명은 256바이트다.
