# 오류 반환·자원 정리·삭제 대상 확인은 각각 무엇을 지키는가

기록일: 2026-10-15

승인 검증 실패를 차단하는 분기부터 같은 핸들로 삭제하는 이유와 RSA 키 재생성까지 연결했다.

## 공부를 시작한 질문

승인 검증이 실패했는데 반환값을 검사하지 않고 삭제 함수를 호출하면 안전한가?

### 처음 이해했던 내용

실패 시 result로 분기해야 한다고 답했다. 이후 자원 정리를 영속 키 삭제와 혼동했고, 핸들을 다시 여는 문제를 접근 충돌로만 생각했다.

## 질의응답에서 수정한 이해

- 성공이 아닌 모든 검증 결과에서 삭제 경로를 차단해야 한다. 서명 불일치뿐 아니라 내부 오류도 거부한다.
- cleanup은 확보한 메모리·핸들의 정리이며, 승인된 영속 객체 삭제와는 다른 작업이다.
- 같은 Object ID로 다시 열어도 같은 키라는 보장은 없다. 지문을 확인한 동일한 핸들로 삭제해야 한다.

## 검증 실패는 삭제 경로에 도달하지 않아야 한다

result = TEE_AsymmetricVerifyDigest(...) 이후 result != TEE_SUCCESS이면 오류 정리 경로로 이동한다. 승인 검증 성공 뒤에도 객체 열기와 지문 비교가 필요하다. 검증 함수를 호출했다는 사실만으로 보호가 성립하지 않는다.

현재 handle_delete_test_key_with_approval은 해시 계산·승인 검증의 결과를 확인한 뒤 delete_persistent_test_signing_key를 호출한다. 성공 여부를 호출 흐름에 반영하는 것이 fail-closed의 핵심이다.

## 실패 시 정리할 것은 성공적으로 확보한 자원

키 열기가 실패했다면 그 호출에서 유효한 키 핸들을 얻은 것이 아니므로 해당 핸들을 닫거나 삭제하지 않는다. 앞서 확보했고 자신이 소유한 다른 자원은 정리해야 한다.

키 열기는 성공했지만 지문이 다르면 오류를 반환하고 열린 핸들만 닫는다. 영속 키는 남긴다. 현재 코드의 close_key 경로는 TEE_CloseObject를 사용한다.

삭제 API 호출 후의 핸들 처리도 그 API의 계약을 따라야 한다. 현재 코드는 TEE_CloseAndDeletePersistentObject1 호출 뒤 핸들을 다시 닫지 않고 TEE_HANDLE_NULL로 설정한다.

## 검사한 핸들을 닫고 다시 열면 생기는 틈

다른 세션이 키를 열어 재열기가 충돌할 수 있다는 답은 맞았다. 더 중요한 경우는 A의 지문을 확인하고 닫은 뒤 다른 실행 흐름이 A를 삭제하고 같은 Object ID에 B를 만드는 상황이다.

그 이름으로 다시 열어 확인 없이 삭제하면 승인받은 A가 아닌 B를 삭제할 수 있다. 이 검사와 사용 사이의 변경 문제를 TOCTOU라고 한다.

현재 삭제 함수는 ACCESS_WRITE_META로 독점적으로 열고, 지문을 확인한 바로 그 핸들로 삭제한다. 중간에 닫고 이름으로 다시 찾지 않는다.

## 같은 Object ID로 재생성해도 같은 키가 아니다

Object ID는 저장 객체를 찾는 이름이지 RSA 키 생성의 입력 시드가 아니다. 같은 이름에 새 키를 생성하면 일반적으로 공개키와 지문도 달라진다. 동일한 키를 복원한 경우는 별개다.

RSA 키 생성 구현은 안전한 난수를 사용해 조건에 맞는 비밀 소수 p, q 등을 생성하고 n = p × q 및 개인키 요소를 계산한다. 개발자가 소수를 직접 선택하는 방식이 아니다.

TEE_AllocateTransientObject는 키를 담을 객체를 할당하고 TEE_GenerateKey가 실제 키를 생성한다. Object ID는 어느 객체를 열지, 공개키 지문은 승인받은 키가 맞는지 확인한다.
