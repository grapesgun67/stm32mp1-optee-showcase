# CA를 신뢰하지 않고 특정 요청을 승인하기

정리일: 2026-10-11 · 소스 대조: bdb8bd8

## 질문의 출발점

CA가 정상인지 검사하는 것인가, 요청이 승인되었는지 검사하는 것인가?

### 이해가 바뀐 지점

노트북을 CA의 정상성을 증명하는 인증기관으로 보던 표현을 수정했다. TA는 미리 등록된 승인자 공개키로 특정 요청의 승인을 확인하며 CA 바이너리의 무결성을 증명하지 않는다.

## 정리한 이해

TA가 요청 상태·챌린지 보관 → CA가 요청 파일 전달 → 노트북 승인자가 서명 → TA가 재구성·소비·검증

### 132바이트와 256바이트의 관계는?

요청은 도메인 16 + UUID 16 + 동작 번호 4 + 공개키 지문 32 + 챌린지 32 + 대상 해시 32로 132바이트다. 현재 RSA-2048 승인 서명은 256바이트다. 서명 파일 안에서 원래 해시를 꺼내 TA 값과 단순 비교하는 방식이 아니다.

### 노트북과 TA는 비밀키를 공유하는가?

노트북은 승인용 개인키를 보관하고 TA에는 대응하는 공개키를 등록한다. 승인 도구는 요청 내용과 예상 키 지문 등을 확인한 뒤 명시적인 사용자 승인을 받는다. TA의 데이터 서명용 개인키는 또 다른 키다.

### CA의 Enter 대기가 보안 통제인가?

파일 전송을 기다리는 사용자 흐름이다. 공격자는 CA를 바꿀 수 있으므로 TA가 상태·형식·서명을 검사해야 한다. 같은 세션을 유지하는 이유는 그 세션에 저장한 챌린지와 요청에 승인을 연결하기 위해서다.

### TA는 정확히 무엇을 검증하는가?

세션에 저장한 필드로 요청을 재구성하고 해시한 뒤, 승인자의 공개키와 받은 서명으로 검증한다. 명령·대상·데이터를 바꾼 승인은 기존 요청에 대한 서명이 아니므로 통과하지 못한다.

### 챌린지와 clear는 왜 필요한가?

새 요청에는 새 챌린지를 사용한다. 현재 구현은 사전 형식 검사를 통과해 실제 처리에 진입하면 성공·검증 실패 모두 요청을 소비한다. 준비 없이 재전송하면 상태 검사, 새 요청에 과거 서명을 쓰면 서명 검사에서 거부된다. 소비는 새 세션 생성이나 영속 키 삭제가 아니다.

### 승인용 개인키가 유출되면?

공격자가 새 요청에도 유효한 승인을 만들 수 있어 승인자의 신뢰가 무너진다. TA 개인키가 직접 유출된 것과는 다르지만 허용된 서비스 기능을 악용할 수 있다. 키 보호·교체·폐기 정책이 필요하다.

## 근거와 확인 범위

기존 공개 시험에는 정상 승인과 변조·다른 키·새 요청에 과거 승인 재사용 거부가 있다. 같은 세션의 모든 실패 분기를 실행했다는 뜻은 아니다.
