# 버퍼의 size는 실제 메모리를 할당하지 않는다

정리일: 2026-10-11 · 소스 대조: bdb8bd8

## 질문의 출발점

tmpref와 memref 중 무엇을 쓰며, 16바이트 버퍼에 size=32를 적으면 어떻게 되는가?

### 이해가 바뀐 지점

길이 필드에 값을 넣는 일과 메모리를 확보하는 일을 구분했다. TA의 길이 검사는 필요하지만 CA의 C 객체 크기를 모두 알아내 주는 장치는 아니라는 점을 정리했다.

## 정리한 이해

CA 버퍼 준비 → 참조·길이·방향 지정 → TA에서 타입·범위 검사 → 출력 길이 확인·각자 정리

### tmpref와 memref의 차이는?

CA tmpref는 buffer와 size를 지정한다. CA memref는 준비된 TEEC_SharedMemory를 parent로 지정하고 offset과 size를 사용한다. TA는 둘 다 자신의 주소 공간에서 사용할 memref.buffer와 size로 받는다. TEMP라는 이름이 스택 할당이나 항상 복사됨을 의미하지는 않는다.

### 실제 16바이트인데 32라고 쓰면?

CA가 잘못된 범위를 선언한 것이다. 같은 메모리 페이지의 뒤쪽까지 접근 가능하면 라이브러리·커널이 원래 C 배열의 경계를 알아서 찾아내지는 못한다. 호출자는 실제 용량을 지켜야 하고 TA도 입력 계약과 출력 한계를 검사해야 한다.

### argv[2] + 2를 전달해도 되는가?

원래 데이터에 최소 2바이트가 있고 포인터와 함께 남은 길이도 줄이면 가능하다. 포인터를 이동시키면서 길이를 그대로 두거나 범위 밖 포인터를 만들면 문제가 된다.

### 출력 버퍼는 누가 준비하는가?

CA가 출력 용량을 준비하고 TA가 필요한 크기를 검사한다. 부족하면 SHORT_BUFFER와 필요한 크기를 반환하는 계약을 사용할 수 있다. 해시 출력은 32바이트 이상 용량을 받아 실제 출력 길이를 32로 돌려주는 식이다.

### 공유 메모리인데 왜 내부 버퍼로 복사하는가?

공유 입력은 Normal World가 바꿀 수 있다. 승인 처리에서는 내부 복사본을 검증·사용해 검사 후 다른 값을 쓰는 문제를 줄인다. 복사만으로 입력이 신뢰되거나 여러 바이트가 원자적으로 읽혔다고 보장되지는 않으므로 복사된 내용의 검증은 계속 필요하다.

개발 저장소 기준. 기존 공개 발췌와 현재 함수명이 다를 수 있다.

- host/main.c: run_echo
- ta/entry.c: handle_echo / handle_sign_with_approval

## 근거와 확인 범위

ECHO 정상·빈 입력 및 파라미터 거부의 기존 실증을 참고한다. 모든 경계값·경쟁 상황을 시험했다고 확장하지 않는다.
